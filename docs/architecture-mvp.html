§ 1 · Scope of Work

Four scoped changes, two developer days

The system is a working full-stack platform: an Angular SPA with modal-driven CRUD and client-side search, a Spring Boot REST API secured by a JWT filter chain, and a MySQL store behind Spring Data JPA. This revision proposes one hardening fix and three product features — chosen for maximum reviewer impact per hour, and deliberately scoped to leave the rest of the codebase untouched.

Build sequence — proportional effort total ≈ 2 dev days
§ 2 · Sheet A — Current State

As built

Every request from the SPA passes through the AuthInterceptor, which attaches the JWT Bearer token and force-logs-out on 401/403. On the server, the JwtAuthenticationFilter validates tokens before requests reach the controllers — but note the amber node: /employee/** is currently permitAll, so the token is never actually required for the data it should protect.

§ 3 · Change Orders

Proposed changes, in build order

Numbered in dependency order: the security fix ships first because every later feature inherits it; error handling ships second because pagination and export reuse its error contract.

CO-00

Enforce authentication on the employee API

Priority EFFORT · 15 MIN

SecurityConfiguration currently declares /employee/** → permitAll(), which leaves the entire JWT stack — filter, token service, interceptor — decorative. Change the matcher to authenticated(). No frontend work: the interceptor already attaches the token to every employee request.

Reviewer signal The first file a technical reviewer opens is the security config. This one line is the difference between “implemented JWT auth” and “pasted JWT boilerplate.”
CO-01

Global error contract + toast notifications

Proposed EFFORT · 0.5 DAY

Backend: one @RestControllerAdvice returning a structured ApiError { timestamp, status, message, path }, mapping UserNotFoundException → 404 and everything else to a clean 500. Frontend: an injectable ToastService plus one toast component, replacing all six alert() calls in the home component.

Reviewer signal Demonstrates a designed error contract between tiers — a production concern, not a tutorial one. Browser alert() is the loudest “tutorial project” tell there is; this removes every instance.
CO-02

Server-side pagination + search

Proposed EFFORT · 1 DAY

Replace GET /employee/all with GET /employee?page=0&size=8&q=term returning Page<Employee>. Spring Data makes this nearly free — JpaRepository already pages; one derived query (findByNameContainingIgnoreCase…) covers search. The Angular service passes the params; the existing search box wires to the server; simple prev/next controls complete it.

Also retires a live bug: the current client-side search silently refetches the full list whenever a query has no matches.

Reviewer signal “Does this scale past 50 rows?” is a classic interview probe. Server-side paging is the canonical proof of thinking beyond the demo dataset — and a ready-made talking point on Pageable and derived queries.
CO-03

CSV export

Proposed EFFORT · 2–3 HRS

One endpoint — GET /employee/export — streaming text/csv with a Content-Disposition: attachment header; a plain PrintWriter suffices, no library. One “Export CSV” button on the frontend downloads the blob; the interceptor attaches the JWT automatically.

Reviewer signal A business feature rather than a CRUD verb — it reads as product thinking. Also the best live-demo moment of the three: click, file lands, done.
